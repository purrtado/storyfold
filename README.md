# Storyfold

Storyfold is a local, single-user interactive roleplay app built with React, TypeScript, Vite, Tailwind CSS, and Bun. A local Bun server persists worlds, characters, campaigns, and transcripts, and streams narrator replies from Z.AI using TanStack AI.

## Getting started

Install [Bun](https://bun.sh), then run:

```sh
bun install
bun run dev
```

`bun run dev` starts the API at `http://127.0.0.1:7834` and Vite at `http://127.0.0.1:5173`. Vite proxies `/api` to the API. Both bind to loopback by default.

To use another backend port, run `STORYFOLD_PORT=7835 bun run dev`. The server and Vite proxy share this override. Frontend ports are fixed at 5173 (development) and 4173 (preview).

For testing from another machine on a trusted local network, run:

```sh
bun run dev --host
```

Open `http://<server-LAN-IP>:5173` on that machine. You can also bind Vite to a specific interface with `bun run dev --host <server-LAN-IP>`. The backend remains on loopback; Settings and chat go through Vite's proxy, and frontend origins on this machine's interface IP addresses are accepted on ports 5173 and 4173.

LAN access is unauthenticated: anyone who can reach Vite can change provider settings or use the saved API key for inference. Use it only on a trusted network; do not expose the app publicly.

Create a production build with:

```sh
bun run build
```

Type-check without building:

```sh
bun run typecheck
```

Run server regression tests with `bun test`. To exercise a production build locally, run `bun run server` and `bun run preview` in separate terminals after building. Set the same `STORYFOLD_PORT` in both terminals if overriding it.

## Provider setup

Open **Settings → Providers** (`/settings/providers`):

1. Enter your Z.AI API key.
2. Choose a **Default model** from the curated dropdown: `GLM-5.3` (default) or `GLM-5.3 Flash` — the two models documented for every GLM Coding Plan tier ([model overview](https://docs.z.ai/devpack/overview)).
3. Save, return to the app, and start or resume a campaign.

Requests use the fixed Coding Plan endpoint `https://api.z.ai/api/coding/paas/v4/chat/completions`; there is no fallback to the separately billed general API. Z.AI's [Coding Plan usage policy](https://docs.z.ai/devpack/usage-policy) restricts subscription use to officially supported tools and products; verify eligibility for your use.

Configuration belongs to this local installation, not a user account. The server saves it at `$XDG_CONFIG_HOME/storyfold/config.json`, or `~/.config/storyfold/config.json` when an absolute XDG path is not configured. The directory is created with mode `0700`, and the file with mode `0600`; the API key is stored in plaintext, protected by your OS user permissions, not encryption.

The saved key is never returned to the browser or stored in browser localStorage. Leave the key field blank when changing the model to retain the existing key, enter a new key to replace it, or use **Remove configuration** to delete the saved setup. Saving validates configuration locally; sending a message exercises the provider.

The API accepts only loopback backend Host headers and frontend origins on localhost or this machine's interface IP addresses, requires JSON for chat/configuration bodies, and bounds request sizes. These safeguards reject unrelated browser origins and DNS rebinding; they do not authenticate LAN clients or other processes running as your OS user.

## Interface

- **Worlds** and **Characters** pages let you create, edit, browse, and select library entries. Characters is the single global cast library (name, description, plus authored appearance, personality, background, baseline motivations, and speaking style). Worlds also provides a grouped location, lore, and opening-scene compendium with create, edit, and delete, plus a World characters section: characters belonging to that world, created, edited, and deleted there, each with **Copy to library** (which warns that library characters can't be deleted). The app keeps these libraries in shared in-memory state for Worlds, Characters, and **New campaign**; page visits and window focus revalidate in the background, and saves update the cache immediately. On **Worlds** and **Characters**, slow cold reads show card skeletons after about 200ms; cold failures offer retry, while failed refreshes preserve the last state (including an empty library) and show a retry notice.
- **New campaign** pairs a world with a protagonist — the character you play — and a narrator-controlled cast. The protagonist and cast are picked from the library and the world's own characters (each option and preview card labelled with its scope); the protagonist is part of the campaign once and is never grounded twice, and every picked character is copied into the campaign at creation. No narrator-controlled characters are selected by default (the protagonist picker defaults to the first character in the library), with **Select all** for the cast plus a preview of included text; every non-scene compendium entry — locations and lore — is captured automatically in creation order, so there is nothing to tick. Opening scenes copy their description into the editable starting situation and confirm before replacing manual edits. A live counter shows the exact opening prompt length against the `NARRATION_CHARACTER_BUDGET`, computed with the same shared `narratorSystemPrompt` helper the server uses; creation is refused with `400 {code:"invalid_input"}` when it exceeds the budget. The starting situation is seeded from the world's suggestion and may be blank; a campaign name is optional. Creating a campaign commits its copied characters, the captured world, and the opening session in one transaction; the opening narration is not started automatically — the empty session shows a **Begin opening** button so you can set up the campaign panel first.
- **Play** shows the campaign name and current session title (marked read-only for closed sessions) in the top bar, the streamed narration, and a composer labelled with your character. Sending an action commits it server-side before the narrator replies; only one reply may be pending per session, so a second submission while one is streaming is rejected as busy without saving the extra input. **Stop** (from any browser tab) settles the reply as an interrupted draft and keeps the partial text, and pressing Escape twice within half a second does the same from anywhere in the session view (a first Escape that closes a menu or dialog does not count); failures settle as failed drafts. Accepted actions are never lost and never resent automatically. While the model reasons, a collapsed **Thinking…** disclosure on the streaming draft can be expanded to follow its thought process live; it is not saved with the reply. The narrator voices every other cast member; your character's words and decisions are never narrated for you. The composer's model picker offers the Settings Default model; an explicit choice applies to that run, is kept in memory for the session, and never rewrites the saved Default. The latest narration carries `‹ n/N ›` swipe controls when it has alternate replies: the arrows (or the ← → keys outside text fields) switch between attempts, and swiping past the newest regenerates. **Regenerate** rewrites the latest narration — or re-asks a trailing action that got no reply — keeping earlier complete replies as swipes; the reply swaps to the usual dashed draft as soon as you ask, and a failed or interrupted trailing draft offers **Retry**. Each message's **⋯** menu (in the active session while nothing is generating in this session; in closed sessions with only **Fork from here**) offers **Edit** — an inline editor, with **Save & regenerate** on your last action — **Delete swipe** when the latest narration has alternates, and **Delete** for this message or this and everything after, each confirmed. **Fork from here** starts a new campaign from the story up to that message — from the open session the campaign's current stats, notes, and relationships are copied as they are now, from a closed session that session's checkpoint is restored (see **Forks**). Swipes exist only on the latest narration, and edits and deletes change only the transcript: campaign notes and relationships are untouched. Closed sessions stay read-only.
- **Speaker attribution**: the narrator opens each paragraph centred on one character with a `[Name]` tag, and Play renders that paragraph unchanged beside the speaker's upright portrait and name, merging consecutive paragraphs by the same speaker along with a single untagged paragraph between two of theirs; other untagged paragraphs stay plain narration. Clicking a campaign character's portrait or name opens their card in the campaign panel — beside play when it is docked, so it stays open while you keep playing, or in the panel sheet on narrower screens. Tags match campaign characters by full name or, when only one character has it, by first name, case-insensitively, at render time, so roster changes apply to the whole transcript. A tag matching no character is a **Walk-on** with a monogram; in the active session its **Add to cast** opens the character form with the name filled in. A paragraph tagged with your character is flagged as written by the narrator. Tags stay in the stored text, so edits, swipes, forks, and the narration budget see them as written.
- **Directing the narrator**: the composer's clapperboard opens an **OOC** field whose note steers only the next reply; the empty session's **Begin opening** takes an optional direction too, and a trailing message's menu offers **Regenerate with direction…**, prefilled with the shown reply's direction. The note reaches the model as `(OOC: …)` after your latest input for that one call and never enters later history; the reply it shaped shows it as **Directed: …**, and each swipe keeps its own.
- The **campaign panel** sits beside play on wide screens and collapses to a rail (preference saved) showing your character's and the cast's avatars plus Notes/Campaign shortcuts; clicking an avatar expands straight to that character. On narrower screens the header's **Campaign** button opens it as a side sheet. It has three tabs: **Characters** (you first, then the cast in creation order; each card shows its avatar, current relationship status, and relationship stats toward and from you as bars, and expands to the character's full portrait when one is uploaded, editable profile and picture, a **Track stats** toggle with the character's stat values, every relationship it owns with editing, and an add-relationship action; **Edit** opens a profile editor with avatar upload, **Save to world** copies the character into the campaign's world, **New character** adds a cast character, and **Delete** — offered for every character but you — removes it together with its relationships), **Notes** (manual campaign state grouped by category), and **Campaign** (the campaign's stats with add, edit, and bank import, the end-session handoff behind one button, the session list with forks and provenance, the leading handoff, and the captured world, starting situation, and compendium). The **sidebar** lists persisted campaigns; reopening one resumes its active session with the full transcript — the same from a reload, a server restart, or another browser. Non-complete narration renders as labelled drafts, and a failed or interrupted latest draft offers a retry.
- Open Settings from the User menu at the bottom of the sidebar or compact rail. General lives at `/settings/general`, with System / Light / Dark theme choices; Providers lives at `/settings/providers`; the stat bank lives at `/settings/stats`; the narrator prompt cards live at `/settings/prompt`. Back to app returns to your campaign without clearing its draft.
- Theme defaults to System and follows browser/OS light/dark changes live; explicitly picking Light or Dark overrides System until you switch back (saved in browser localStorage). The User avatar is a display-only placeholder, not an account.
- Collapse the sidebar on desktop to a narrow icon rail (preference saved); its logo toggles expansion, with the sidebar icon revealed on hover or keyboard focus. The route-agnostic rail always offers New campaign, Worlds, and Characters (the full layout also lists campaigns); on mobile it remains a slide-in drawer. Expanding lays the full sidebar out at its resting width inside the clipped shell and reveals it, so its labels never re-wrap mid-animation.
- Press Enter to send an action or Shift+Enter for a newline. The transcript keeps new messages in view while you are near the bottom and hands scrolling back to you the moment you scroll up to read.

Settings uses browser-history routes. Production hosting must serve `index.html` for application URLs such as `/settings/general` so direct links and refreshes work (Vite dev/preview already handle this).

## Worlds, campaigns, and server-owned play (M1)

Worlds, characters, campaigns, sessions, and messages persist in a local SQLite database (Bun's `bun:sqlite`, no ORM) at `<data dir>/storyfold.db`. The data dir defaults to the configuration directory (`~/.config/storyfold`); override it with `STORYFOLD_DATA_DIR` (a directory) and the credentials directory with `STORYFOLD_CONFIG_DIR`. The startup sweep settles any reply still `pending` from a previous process as `interrupted`; generation never auto-resumes.

Creating a campaign copies the picked characters — library or world characters — into the campaign and captures the world and its non-scene compendium, creates the opening session, and links it as the campaign's active session in one committed transaction — later library and world edits affect new campaigns only. Messages get server-assigned `position` order; `speaker_name` labels are captured at send time and never re-derived from the library (a player's turn is always spoken as the protagonist's current name).

The browser never owns play history. It sends a session id plus new input (`POST /api/sessions/:id/messages`), an opening request (`POST /api/sessions/:id/opening`, accepted only while the session is still empty — `409 {code:"already_opened"}` otherwise; retries of a failed opening go through regenerate), or a regeneration (`POST /api/sessions/:id/regenerate {model?}`); all three accept an optional `direction` string (blank means none), stored on the reserved reply and appended as `(OOC: …)` to the last player message of that call only. All three return a TanStack AI SSE stream and carry `x-storyfold-accepted` plus `x-storyfold-player-message-id` / `x-storyfold-pending-message-id` headers identifying the saved rows. The player's turn commits before the model is invoked; only one `pending` assistant reply may exist per session (concurrent submissions get `409 {code:"busy"}` with nothing saved). The server owns the reply lifecycle: completion requires normal-stop evidence from the provider, Stop (`POST /api/sessions/:id/stop`, works from any browser) or a disconnect settles the reply `interrupted` with its partial text preserved, and provider failures settle it `failed` — accepted player input always survives, and only completed narration plus accepted input feed later model calls, in position order, under the narrator prompt built from the saved prompt cards and the campaign's characters and captured world. Nothing is compacted or truncated; a context-limit failure surfaces as a `context_limit` error.

Narration keeps its completed attempts: alternate replies share one `position` with a `selected` flag, only the selected row feeds the model and the transcript, and every transcript row carries `variant_ids` (oldest first) and `variant_index` — populated on the trailing narration only, its drafts included. The latest narration can be switched (`POST /api/sessions/:id/messages/:message_id/select` → `{messages}`, any draft left behind discarded), lose one alternate (`DELETE /api/sessions/:id/messages/:message_id?scope=variant`; the sole remaining alternate answers `409 {code:"sole_variant"}` — delete the message instead), a message (with its alternates) or everything from a point on can be removed (`DELETE /api/sessions/:id/messages/:message_id` or `?scope=after`, both → `{messages}`), and a completed message can be edited in place (`PATCH /api/sessions/:id/messages/:message_id {content}` → `{message}`; drafts answer `409 {code:"not_editable"}`, growth past the narration budget `413 {code:"context_limit"}`; role, speaker name, and position never change). Only the latest narration can be switched or swiped (`409 {code:"not_trailing"}`), regeneration has nothing to work with on an empty session (`409 {code:"nothing_to_regenerate"}`), and all of these run the same guards as play: `409 {code:"busy"}`, `409 {code:"session_closed"}`, and `404` for another session's ids. Edits and deletes change only the transcript — campaign notes and relationships are untouched. Browse the domain via `GET/POST /api/worlds` and `GET/PATCH /api/worlds/:id`, `GET/POST /api/characters` and `GET/PATCH /api/characters/:id`, `GET/POST /api/campaigns` and `GET /api/campaigns/:id`, and `GET /api/sessions/:id` (+ `/messages`). A missing provider key answers `400 {code:"no_provider", accepted:true, ...ids}` with the input saved and the draft marked failed.

## Characters at three scopes (M2 revision)

One profile shape exists at every scope (`CHARACTER_PROFILE_FIELDS` in `shared/domain.ts`): a required name and description plus lean authored fields — appearance, personality, background, baseline motivations, speaking style — each optional and empty when unauthored; there is no attribute engine. A character lives in the global library (`world_id` null), in one world (`world_id` set), or as a campaign's own copy; moving between scopes is always a copy, nothing syncs, and no provenance is kept.

The library is listed and created under `GET/POST /api/characters` and read and edited under `GET/PATCH /api/characters/:id`; definitions are edited in place, and library characters cannot be deleted (`DELETE /api/characters/:id` answers `400 {code:"invalid_input"}`). World characters are created and listed under `GET/POST /api/worlds/:id/characters`; the same `/api/characters/:id` routes read, edit, and delete them (`DELETE` answers `{ok:true}` for world characters, `404` for unknown ids). **Copy to library** (`POST /api/characters/:id/copy-to-library` → `201 {character}`) copies a world character's profile and picture into the library — the Worlds page warns that library characters can't be deleted — and a library character answers `400`.

Each character at any scope may carry one picture. `PUT /api/characters/:id/avatar` takes the image's raw bytes (not multipart) with `content-type` `image/png`, `image/jpeg`, `image/webp`, or `image/gif`, capped at 2 MiB (`413` over); the magic bytes must match the declared type, and SVG or any other format is rejected (`415` unsupported type, `400` mismatch). Images are stored content-addressed — the lowercase hex sha256 of the bytes — in an `images` table, deduplicated by hash and immutable; `character_avatars` points a character at one, and `DELETE /api/characters/:id/avatar` clears the pointer (the bytes stay). Every character response carries `avatar_id: string | null`, and `GET /api/images/:id` serves the stored bytes with the stored `content-type` plus `cache-control: public, max-age=31536000, immutable` (unknown ids: `404`). Like all mutations, avatar uploads require a trusted local Origin; copies at other scopes share the stored image by id.

Campaign creation takes `{world_id, protagonist_id, cast_character_ids?, starting_situation, name?}`: the character ids must be library characters or characters of that world (anything else answers `404`), duplicate entries in `cast_character_ids` or the protagonist appearing among them answer `400`, and — in the same transaction that captures `world_snapshot` (`{name, setting_brief, entries}`) and creates the opening session — every picked character is copied by value into `campaign_characters`, protagonist first, then cast in creation order (`protagonistOf(campaign)` returns the protagonist). A copy carries `avatar_id` by value like every field: replacing or removing a library or world picture later never rewrites an existing campaign, `avatar_id` never enters narration prompts (images are display-only), and narration never re-resolves captured ids against the live libraries.

A campaign's characters are its own copies, edited in the campaign: `GET /api/campaigns/:id/characters` lists them, `POST {profile}` adds a cast character, `PATCH /api/campaigns/:id/characters/:cid {partial profile}` edits the copy in place, `DELETE` removes any character but the protagonist (`400`) together with its relationships, and `PUT/DELETE /api/campaigns/:id/characters/:cid/avatar` manages the copy's picture (raw bytes exactly like library avatars). **Save to world** (`POST /api/campaigns/:id/characters/:cid/save-to-world` → `201 {character}`) copies the current profile and picture into the campaign's world as a new world character. Every campaign character write except save-to-world answers `409 {code:"busy"}` while a narration run is pending.

## World compendium (M2)

World entries — locations, lore, and opening-scene templates — persist in a `world_entries` table and are managed world-scoped under `GET/POST /api/worlds/:world_id/entries` and `PATCH/DELETE /api/worlds/:world_id/entries/:entry_id` (`200 {ok:true}` on delete). An entry id only ever resolves inside its own world's URL, so another world's entry is indistinguishable from a missing one (`404`).

Campaign creation takes no entry list: every non-scene entry of the world — locations and lore — is captured automatically, in creation order, into `world_snapshot.entries` (`[{id, kind, name, description}]`) inside the same creation transaction. Scenes are opening templates only — selecting one copies its description into the editable starting situation in the UI and is never captured as grounding. Later library edits and deletes never rewrite an existing campaign, and narration is grounded only on that captured list — the live library is never re-resolved.

Entry mutations, including deletion, require a trusted `Origin` header.

## Campaign state, sequential sessions, and forks (M3)

**Manual campaign state** is campaign-owned text the player curates: categories `goal`, `knowledge`, `internal`, and `journal`, each item a required free-text `subject` and `content`, with server timestamps; notes never link to characters or entries. Items live under `GET/POST /api/campaigns/:id/state` (list in creation order; create returns the bare item) and `PATCH/DELETE /api/campaigns/:id/state/:item_id` (delete answers `200 {ok:true}`). An item id resolves only inside its own campaign's URL, like entries and campaign characters. Journal chronology is the immutable `created_at` order — edits never reorder a journal. Mutations are refused with `409 {code:"busy"}` while a narration run is pending in the campaign's active session; nothing is saved by a refused request.

**Directional relationships** are stored separately from manual state notes (and are not part of the manual campaign-state categories). `GET /api/campaigns/:id/relationships` returns `{relationships}`. A relationship runs between two characters of the campaign — `source_id` and `target_id` must identify campaign characters, else `400` — and a campaign holds at most 100 relationships. Create a directed pair with `POST /api/campaigns/:id/relationships {source_id, target_id, how_met?, status?, known_facts?, stats?}`; reverse direction is a separate relationship, and duplicate ordered pairs are rejected. A relationship carries the fixed fields `how_met` and `status`, the `known_facts` list, and every relationship stat of the campaign — a new relationship starts with each stat at its default. `PATCH /api/campaigns/:id/relationships/:rid {how_met?, status?, known_facts?, stats?}` — last save wins, and `stats` merge into the existing values. `DELETE` removes that relationship.

**Sessions are sequential and explicitly reviewed.** `POST /api/campaigns/:id/sessions {title, handoff}` closes the campaign's one open session (recording its `closed_at` and the reviewed `handoff`), stores one JSON checkpoint of the campaign's changeable state — its stats, characters, notes, and relationships — in `session_checkpoints` at that boundary, opens the next session, and moves `active_session_id` — all in one committed transaction; the response is `{session}`. `GET /api/campaigns/:id/sessions` lists them in story order as `{sessions: [...]}`. Closed sessions are read-only: play and opening requests answer `409 {code:"session_closed"}` — a guard enforced again inside the write transaction, so a close that races an in-flight play request can never write into the closed session. Every open session accepts an opening narration only while it is empty (`409 {code:"already_opened"}` once any message exists, including a failed or interrupted draft; retries go through regenerate): the campaign's first opens from the starting situation, later sessions and forks continue from their leading handoff.

Narration is grounded per session on the campaign's copied characters and captured world snapshot, the **current** campaign state, the **handoff leading into this session**, and **this session's history only** — a later session never sees the original starting situation or any earlier session's turns, and nothing is dropped silently: closed transcripts stay readable via `GET /api/sessions/:id/messages`.

**Context boundary.** One size budget covers every narrator call: `NARRATION_CHARACTER_BUDGET` (160,000 characters) in `shared/narration.ts` counts the narrator system prompt plus the session's completed history (selected player inputs plus completed narration), plus the request's direction note. It is checked per generation request — player turn, opening, and regenerate — and on message edits that grow a selected message; a request that would exceed it is refused with `413 {code:"context_limit", accepted:false}` and a message telling you to shorten the campaign's notes or relationships, or begin the next session with a handoff. No message is saved and nothing is ever truncated; the budget bounds the size of the model call, not a token window.

**Forks.** `POST /api/sessions/:id/messages/:message_id/fork {name}` (201 `{campaign, session}`) starts a new independent campaign from any message of the open or a completed session: the captured world snapshot and starting situation are copied by value, the campaign's stats and characters come with it, the transcript carries the selected messages up to and including that message (drafts and unselected swipes excluded, renumbered from 1), and the handoff that grounded the source session grounds the fork's first session. From the open session the campaign's **current** state — stats, characters, notes, relationships — becomes the fork's own; from a closed session the session's stored checkpoint is restored instead; both are written under new ids with relationship endpoints remapped to the new character ids, so later edits to the origin campaign's state or library never leak into the fork, and the origin keeps playing on unaffected. The origin is recorded on the campaign as `forked_from_campaign_id` / `forked_from_session_id` and never re-resolved afterwards; ancestor transcripts stay reachable through the recorded origin session id. A message id from another session answers `404`; a pending reply answers `409 {code:"busy"}`.

## Stats (M5)

A **stat definition** is a reusable bounded meter: `applies_to` (`character` or `relationship`, immutable after creation), required `label`, `description`, `low_label`, and `high_label` text of at most 500 characters each, integer `min` < `max` and a `default_value` inside the range (magnitudes capped at 1000), and a `color` from the fixed palette `slate`, `red`, `orange`, `amber`, `green`, `teal`, `blue`, `violet`, `pink` (light and dark values live in `src/index.css` as `--stat-<token>`); labels are unique per kind within their scope (case-insensitive), and each scope holds at most 12 stats per kind. The **stat bank** is edited under **Settings → Stats** (`/settings/stats`) through `GET/POST /api/stats` and `PATCH/DELETE /api/stats/:id`; a fresh database seeds it with Health, Stamina, Stress, and Morale for characters and Trust, Affection, Respect, and Tension for relationships, all 0–10.

**World stats** are listed and created under `GET/POST /api/worlds/:id/stats` and share the `PATCH/DELETE /api/stats/:id` routes — one set of routes whose id resolves in the bank or any world. Bank stats can be imported only when a world is created: the create-world form's stat picker sends `POST /api/worlds {name, setting_brief, suggested_starting_situation, stat_ids?}` and the chosen bank stats are copied in (unknown or non-bank ids answer `404`); there is no later import. Deleting a bank or world stat never touches campaigns that already copied it.

**Campaign stats** are the campaign's own copies of the world's stats, created in the same transaction as the rest of the campaign (`campaign.stats`, character stats first, then relationship stats, each in creation order) — later bank and world edits never rewrite an existing campaign. They are managed in the campaign panel's **Campaign** tab: `POST /api/campaigns/:id/stats` defines one, `PATCH/DELETE /api/campaigns/:id/stats/:sid` edit or remove it, and `POST /api/campaigns/:id/stats/import {stat_ids}` copies bank stats — refused with `400 {code:"invalid_input"}` once the story has begun, that is once the campaign holds any message — every campaign response carries this as `story_begun`, and the panel shows the import button only while it is `false`. An added stat gives its default to every opted-in character (or to every relationship), a changed `min`/`max` clamps existing values into the new range, and a deletion removes the value from every character and relationship. Every campaign-stat write answers `409 {code:"busy"}` while a narration run is pending.

**Stat tracking is per character and all-or-nothing**: a campaign character either carries every character stat or none (`stats_enabled` plus a `stats` map of stat id to integer). The protagonist starts opted in with every stat at its default; cast characters — picked at creation or added later — start off. `PATCH /api/campaigns/:id/characters/:cid` accepts `stats_enabled` and a partial `stats` map: turning tracking on fills every character stat with its default, turning it off clears the values, values may only be set while tracking is on (`400` otherwise), and unknown, non-integer, or out-of-range values answer `400`.

**Narration** renders the stats legend once — `Stats (scale and meaning):` followed by one line per stat with its kind, range, description, and both end labels — appends values like `[Health 7/10, Stress 2/10]` to each opted-in character's line, and ends each relationship line with its values (`Trust 4/10`). `NarrationContext` carries `stats` (definitions with ids), characters as `CharacterPrompt` (profile plus `stats_enabled` and `stats`), and relationships as `RelationshipPrompt` (`source_name`, `target_name`, `how_met`, `status`, `known_facts`, `stats`).

## Narrator prompt cards

The narrator system prompt is one global, ordered list of **prompt cards**, edited under **Settings → Prompt** (`/settings/prompt`) and applied live to every campaign. A card has a `title` (an editor label, never sent), a `body`, and an `enabled` switch; the prompt is the enabled bodies, top to bottom, separated by blank lines. Bodies may use the placeholders `{{world_name}}`, `{{world_brief}}`, `{{situation}}` (starting situation, or the handoff after session 1), `{{stats}}`, `{{protagonist_name}}`, `{{protagonist}}`, `{{cast}}`, `{{compendium}}`, `{{notes}}`, `{{relationships}}`, and `{{continuation}}` (open, continue from the handoff, or continue the story); a card using any placeholder that is empty for the campaign — no cast, no notes — is left out, so its heading never introduces nothing. Any other `{{…}}` is refused on save. A fresh workspace starts with `DEFAULT_PROMPT_CARDS` (`shared/narration.ts`), which reproduce the previous fixed prompt; the `[Name]` speaker-tag and OOC cards are editable too, so disabling them stops speaker attribution and directions from working.

Cards are served by `GET /api/prompt-cards` (`{cards}` in order), created with `POST {title, body?, enabled?}` (appended last; `201 {card}`), edited with `PATCH /api/prompt-cards/:id {title?, body?, enabled?}`, and deleted with `DELETE`. `PUT /api/prompt-cards/order {ids}` sets the order and must name every card exactly once; `POST /api/prompt-cards/reset` replaces every card with the defaults. Both answer `{cards}`. Edits apply from the next narrator call, and the narration budget counts the rendered prompt.

Message editing and prompt-card bodies use a plain-text editor with automatic bracket and quote pairing and find/replace. Use the **Find & replace** button or `Ctrl/⌘+F`.

## Development workspace

The schema carries a version (`PRAGMA user_version`, currently 5). Version 3 and 4 workspaces upgrade in place on startup (version 3 gains the narration `direction` column; both gain the default prompt cards; nothing else changes); otherwise there are no migrations or compatibility layer: a workspace database created by an older schema is refused at startup with a message to delete it, and the Vite proxy answers every `/api` request with 500 meanwhile. Point `STORYFOLD_DATA_DIR` at a fresh directory to use the new schema; this does not delete, reset, or overwrite the existing database, which remains untouched:

```sh
STORYFOLD_DATA_DIR=$HOME/.local/share/storyfold-m5 bun run dev --host
```

`bun run dev` starts the full stack (API and Vite) against that data directory. Backend tests always run against isolated temporary databases.

## UI components

The composer, transcript scroller, tooltips, and theme indicator are adapted from [beUI](https://beui.dev) registry sources (installed by copying and trimming the component code, not via the shadcn CLI):

- [Prompt Input](https://beui.dev/components/agents/prompt-input) — composer form, keyboard submission with IME safety, send-button motion, and a Stop control during generation. The model picker offers the provider Default with an optional per-message override; attachment UI is omitted. Auto-grow uses the repo's `field-sizing` CSS instead of the registry's measurement mirror, so browsers without `field-sizing` show a fixed-height scrolling composer. Focus uses the existing rounded composer border; forced-colors mode retains a visible textarea outline.
- [Message Scroller](https://beui.dev/components/agents/message-scroller) — reader-aware transcript viewport. Deviations: viewport resizes (composer growth, mobile drawer) re-align the live edge instantly while you are following, wheel, touch, and upward keyboard scrolling interrupt an in-flight follow, and the optional message navigation rail is omitted.
- [Tooltip](https://beui.dev/components/motion/tooltip) — hover/focus tooltips on the sidebar rail.
- [Tabs](https://beui.dev/components/motion/tabs) — shared-layout spring indicator adapted to the settings theme radios, without tab panels or overflow controls. The pill slides between choices; reduced-motion users get an instant selection change.
- [Collapsible](https://beui.dev/components/motion/collapsible) — prompt card expand/collapse on **Settings → Prompt**. Controlled only, with the repo's button styling on the trigger; the `render` slot is omitted. The cards' reorder list shares its layout spring, so expanding a card moves its neighbours without stretching their text.

Dependencies added for these components: `motion` (reduced-motion-aware animation), `@floating-ui/dom` (tooltip positioning), `lucide-react` (send icon), and `clsx` + `tailwind-merge` (the `cn` class helper).

The User menu uses Radix Dropdown Menu; page navigation uses React Router. Settings theme choices use native radios for keyboard navigation and accessible selection.
