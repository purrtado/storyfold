# Storyfold

Storyfold is a local, single-user interactive roleplay app built with React, TypeScript, Vite, Tailwind CSS, and Bun. A local Bun server persists worlds (with their characters, relationships, and stats), chats, and transcripts, and streams narrator replies from any OpenAI-compatible chat-completions or Anthropic Messages provider using TanStack AI.

## Getting started

Install [Bun](https://bun.sh), then run:

```sh
bun install
bun run dev
```

`bun run dev` starts the API at `http://127.0.0.1:7834` and Vite at `http://127.0.0.1:5173`. Vite proxies `/api` to the API. Both bind to loopback by default.

To use another backend port, run `STORYFOLD_PORT=7835 bun run dev`. The server and Vite proxy share this override. Frontend ports are fixed at 5173 (development) and 4173 (preview).

For testing from another machine on a trusted local network, run:

```sh
bun run dev --host
```

Open `http://<server-LAN-IP>:5173` on that machine. You can also bind Vite to a specific interface with `bun run dev --host <server-LAN-IP>`. The backend remains on loopback; Settings and chat go through Vite's proxy, and frontend origins on this machine's interface IP addresses are accepted on ports 5173 and 4173.

LAN access is unauthenticated: anyone who can reach Vite can change provider settings or use the saved API key for inference. Use it only on a trusted network; do not expose the app publicly.

Create a production build with:

```sh
bun run build
```

Type-check without building:

```sh
bun run typecheck
```

Run server regression tests with `bun test`. To exercise a production build locally, run `bun run server` and `bun run preview` in separate terminals after building. Set the same `STORYFOLD_PORT` in both terminals if overriding it.

## Provider setup

Open **Settings → Providers** (`/settings/providers`):

1. **Add provider**, optionally starting from a preset (Anthropic, OpenAI, OpenRouter, Z.AI Coding Plan, Ollama, LM Studio) that fills in the name, API, and base URL, and enter an API key if the provider needs one.
2. Expand the provider to edit it or manage its **Models**: switch off the ones you don't want in the composer (filter the list and use **Enable/Disable all** for long lists), **Refresh** the list from the provider, or add a model id by hand.
3. Return to the app, pick the provider and model in the composer, and start or resume a chat.

Each provider is a name, an API, a base URL, and an optional API key (local servers such as Ollama or LM Studio need none; keyless requests send no credential header). The API is fixed when the provider is added:

- **OpenAI chat completions** (`openai`): requests go to `<base URL>/chat/completions` with `Authorization: Bearer <key>`, and models are listed from `GET <base URL>/models`. Base URLs include the version, e.g. `https://api.openai.com/v1`.
- **Anthropic Messages** (`anthropic`): requests go to `<base URL>/v1/messages` with `x-api-key: <key>`, and models are listed from `GET <base URL>/v1/models`. Base URLs omit the version, e.g. `https://api.anthropic.com`, matching `ANTHROPIC_BASE_URL` for Anthropic-compatible gateways. Prompt caching is on: each request marks the narrator system prompt and the latest player message with `cache_control`, so the next turn reads the shared prefix from Anthropic's 5-minute cache. Prompts shorter than the model's minimum cacheable length are not cached. Cache reads appear as cached tokens in the reply's prompt usage.

The server caches each model list in memory: a list younger than an hour is served as-is, an older one is served immediately while a background refresh runs, and a failed fetch keeps the last known list. Changing a provider's base URL or key drops its cached list. Every listed model is enabled by default; disabling one is sticky, so it stays hidden even if the provider stops and later resumes listing it. Model ids can also be added by hand for providers whose model list is missing or incomplete. Providers saved before the API choice existed load as OpenAI chat completions.

The selected provider and model is one global choice saved with the configuration, so it survives reloads and applies to every chat. Installs predating multiple providers are migrated on read: the saved Z.AI Coding Plan key becomes a provider with its GLM models listed by hand and its saved model selected. Z.AI's [Coding Plan usage policy](https://docs.z.ai/devpack/usage-policy) restricts subscription use to officially supported tools and products; verify eligibility for your use.

Configuration belongs to this local installation, not a user account. The server saves it at `$XDG_CONFIG_HOME/storyfold/config.json`, or `~/.config/storyfold/config.json` when an absolute XDG path is not configured. The directory is created with mode `0700`, and the file with mode `0600`; API keys are stored in plaintext, protected by your OS user permissions, not encryption.

Saved keys are never returned to the browser or stored in browser localStorage, and are never part of logs, error messages, or cache keys; upstream errors reach the browser only as fixed messages. Editing a provider's base URL keeps its saved key; use **Remove key** to delete it. Model-list fetches refuse redirects, so a key is only ever sent to the configured host.

API: `GET /api/providers` → `{providers, selection}` (each provider reports `api` and `has_api_key`, never the key), `POST /api/providers {name, api? ("openai" default | "anthropic"), base_url, api_key?, manual_models?}`, `PATCH /api/providers/:id {name?, base_url?, api_key? (null removes), disabled_models?, manual_models?}`, `DELETE /api/providers/:id`, `GET /api/providers/:id/models[?refresh=1]` → `{models: [{id, enabled, manual}], fetched_at, error}`, and `PUT /api/model-selection {provider_id, model}`.

The API accepts only loopback backend Host headers and frontend origins on localhost or this machine's interface IP addresses, requires JSON for chat/configuration bodies, and bounds request sizes. These safeguards reject unrelated browser origins and DNS rebinding; they do not authenticate LAN clients or other processes running as your OS user.

## Interface

- **Worlds** lists your worlds and creates one, optionally copying stats in from the stat bank. A world is the save: its page is the hub for the brief, the grouped location, lore, and opening-scene compendium with create, edit, and delete — locations and lore take optional keywords, a priority, and a stay-active count, and are then sent only to replies whose recent messages mention them (see [Keyword entries](#world-compendium-m2)) — the world's characters (profile, picture, **Knows**, stat tracking, and context mode), relationships, world stats with bank import, its chats, and the **New chat** form. Everything there is edited live: chats read the world on every reply. The app keeps worlds in shared in-memory state; page visits and window focus revalidate in the background, and saves update the cache immediately. Slow cold reads show card skeletons after about 200ms; cold failures offer retry, while failed refreshes preserve the last state and show a retry notice.
- **New chat** starts a playthrough of the world: pick the protagonist — the world character you play, preselected as the protagonist of the world's most recently updated chat — and write an optional opening, free text that tells the narrator how the story starts. Opening scenes from the compendium prefill the opening and confirm before replacing manual edits. The opening is the first message of every narrator call for the chat, and a chat never writes to its world. A chat's title defaults to the first line of its opening, can be renamed, and **Discard** deletes the chat with its transcript after a confirmation. Creation is refused with `400 {code:"invalid_input"}` when the system prompt plus the opening message already exceed the `NARRATION_TOKEN_BUDGET`. The opening narration is not started automatically — the empty chat shows a **Begin opening** button so you can adjust the world first.
- **Play** shows the chat title in the top bar, the streamed narration, and a composer labelled with your character. Sending an action commits it server-side before the narrator replies; only one reply may be pending per chat, so a second submission while one is streaming is rejected as busy without saving the extra input. **Stop** (from any browser tab) settles the reply as an interrupted draft and keeps the partial text, and pressing Escape twice within half a second does the same from anywhere in the chat view (a first Escape that closes a menu or dialog does not count); failures settle as failed drafts. Accepted actions are never lost and never resent automatically. While the model reasons, a collapsed **Thinking…** disclosure on the streaming draft can be expanded to follow its thought process live; it is not saved with the reply. The narrator voices every other cast member; your character's words and decisions are never narrated for you. The composer's model picker lists providers; hovering, clicking, or pressing → on one opens its enabled models. The choice is saved globally, so it survives reloads and follows you to every chat; if the saved model is switched off or its provider removed, the picker falls back to the first enabled model, preferring the same provider. The latest narration carries `‹ n/N ›` swipe controls when it has alternate replies: the arrows (or the ← → keys outside text fields) switch between attempts, and swiping past the newest regenerates. **Regenerate** rewrites the latest narration — or re-asks a trailing action that got no reply — keeping earlier complete replies as swipes; the reply swaps to the usual dashed draft as soon as you ask, and a failed or interrupted trailing draft offers **Retry**. Each message's **⋯** menu (while nothing is generating in the chat) offers **Edit** — an inline editor, with **Save & regenerate** on your last action — **Delete swipe** when the latest narration has alternates, and **Delete** for this message or this and everything after, each confirmed. **Branch from here** starts a new chat in the same world from the story up to that message (see **Branches**). Swipes exist only on the latest narration, and edits and deletes change only the transcript: the world is untouched.
- **Speaker attribution**: the narrator opens each paragraph centred on one character with a `[Name]` tag, and Play renders that paragraph unchanged beside the speaker's upright portrait and name, merging consecutive paragraphs by the same speaker along with a single untagged paragraph between two of theirs; other untagged paragraphs stay plain narration. Clicking a character's portrait or name opens their card in the world panel — beside play when it is docked, so it stays open while you keep playing, or in the panel sheet on narrower screens. Tags match world characters by full name or, when only one character has it, by first name, case-insensitively, at render time, so roster changes apply to the whole transcript. A tag matching no character is a **Walk-on** with a monogram; its **Add to world** opens the character form with the name filled in. A paragraph tagged with your character is flagged as written by the narrator. Tags stay in the stored text, so edits, swipes, branches, and the narration budget see them as written.
- **Directing the narrator**: the composer's clapperboard opens an **OOC** field whose note steers only the next reply; the empty chat's **Begin opening** takes an optional direction too, and a trailing message's menu offers **Regenerate with direction…**, prefilled with the shown reply's direction. The note reaches the model as `<ooc>…</ooc>` after your latest input for that one call and never enters later history; the reply it shaped shows it as **Directed: …**, and each swipe keeps its own.
- The **world panel** sits beside play on wide screens and collapses to a rail (preference saved) showing your character's and the other characters' avatars; clicking an avatar expands straight to that character. On narrower screens the header's button opens it as a side sheet. It edits the **world** live — new replies see every change — in tabs for **Characters** (your protagonist first, then the other characters in creation order; each card shows its avatar, current relationship status, and relationship stats toward and from you as bars, and expands to the character's full portrait when one is uploaded, editable profile and picture, a **Track stats** toggle with the character's stat values, every relationship it owns with editing, and an add-relationship action; **New character** adds a world character, and **Delete** — offered for every character that is not a chat's protagonist — removes it together with its relationships) and the world's compendium. The **sidebar** lists the world nav and your recent chats; reopening one resumes it with the full transcript — the same from a reload, a server restart, or another browser. Non-complete narration renders as labelled drafts, and a failed or interrupted latest draft offers a retry.
- Open Settings from the User menu at the bottom of the sidebar or compact rail. General lives at `/settings/general`, with System / Light / Dark theme choices; Providers lives at `/settings/providers`; the stat bank lives at `/settings/stats`; the narrator prompt cards live at `/settings/prompt`. Back to app returns to your chat without clearing its draft.
- Theme defaults to System and follows browser/OS light/dark changes live; explicitly picking Light or Dark overrides System until you switch back (saved in browser localStorage). The User avatar is a display-only placeholder, not an account.
- Collapse the sidebar on desktop to a narrow icon rail (preference saved); its logo toggles expansion, with the sidebar icon revealed on hover or keyboard focus. The route-agnostic rail always offers Worlds (the full layout also lists recent chats); on mobile it remains a slide-in drawer. Expanding lays the full sidebar out at its resting width inside the clipped shell and reveals it, so its labels never re-wrap mid-animation.
- Press Enter to send an action or Shift+Enter for a newline. The transcript keeps new messages in view while you are near the bottom and hands scrolling back to you the moment you scroll up to read.

Settings uses browser-history routes. Production hosting must serve `index.html` for application URLs such as `/settings/general` so direct links and refreshes work (Vite dev/preview already handle this).

## Worlds, chats, and server-owned play (M1)

Worlds, their characters, chats, and messages persist in a local SQLite database (Bun's `bun:sqlite`, no ORM) at `<data dir>/storyfold.db`. The data dir defaults to the configuration directory (`~/.config/storyfold`); override it with `STORYFOLD_DATA_DIR` (a directory) and the credentials directory with `STORYFOLD_CONFIG_DIR`. The startup sweep settles any reply still `pending` from a previous process as `interrupted`; generation never auto-resumes.

**The world is the save.** A world owns its brief, compendium entries, characters, relationships, and stats, and every chat reads them live: nothing is copied into a chat, so an edit to the world applies from the next reply of every chat in it. A chat is one disposable playthrough: a `protagonist_id` (a character of the world, picked per chat), a `title`, an `opening`, and a transcript. A chat never writes to its world, and discarding it (`DELETE /api/chats/:id`) deletes only the chat and its messages. Messages get server-assigned `position` order; `speaker_name` labels are captured at send time (a player's turn is always spoken as the protagonist's current name).

The browser never owns play history. It sends a chat id plus new input (`POST /api/chats/:id/messages`), an opening request (`POST /api/chats/:id/opening`, accepted only while the chat is still empty — `409 {code:"already_opened"}` otherwise; retries of a failed opening go through regenerate), or a regeneration (`POST /api/chats/:id/regenerate`); all three accept an optional `provider_id` plus `model` pair (omitted means the saved selection; no usable selection settles the reply as failed with `400 {code:"no_provider"}`) and an optional `direction` string (blank means none), stored on the reserved reply and appended as `<ooc>…</ooc>` to the last player message of that call only. All three return a TanStack AI SSE stream and carry `x-storyfold-accepted` plus `x-storyfold-player-message-id` / `x-storyfold-pending-message-id` headers identifying the saved rows. The player's turn commits before the model is invoked; only one `pending` assistant reply may exist per chat (concurrent submissions get `409 {code:"busy"}` with nothing saved). The server owns the reply lifecycle: completion requires normal-stop evidence from the provider, Stop (`POST /api/chats/:id/stop`, works from any browser) or a disconnect settles the reply `interrupted` with its partial text preserved, and provider failures settle it `failed` — accepted player input always survives, and only completed narration plus accepted input feed later model calls, in position order, under the narrator prompt built on every call from the saved prompt cards and the live world. Nothing is compacted or truncated; a context-limit failure surfaces as a `context_limit` error.

Narration keeps its completed attempts: alternate replies share one `position` with a `selected` flag, only the selected row feeds the model and the transcript, and every transcript row carries `variant_ids` (oldest first) and `variant_index` — populated on the trailing narration only, its drafts included. The latest narration can be switched (`POST /api/chats/:id/messages/:message_id/select` → `{messages}`, any draft left behind discarded), lose one alternate (`DELETE /api/chats/:id/messages/:message_id?scope=variant`; the sole remaining alternate answers `409 {code:"sole_variant"}` — delete the message instead), a message (with its alternates) or everything from a point on can be removed (`DELETE /api/chats/:id/messages/:message_id` or `?scope=after`, both → `{messages}`), and a completed message can be edited in place (`PATCH /api/chats/:id/messages/:message_id {content}` → `{message}`; drafts answer `409 {code:"not_editable"}`, growth past the narration budget `413 {code:"context_limit"}`; role, speaker name, and position never change). Only the latest narration can be switched or swiped (`409 {code:"not_trailing"}`), regeneration has nothing to work with on an empty chat (`409 {code:"nothing_to_regenerate"}`), and all of these run the same guards as play: `409 {code:"busy"}`, and `404` for another chat's ids. Edits and deletes change only the transcript — the world is untouched. Browse the domain via `GET/POST /api/worlds` and `GET/PATCH /api/worlds/:id`, `GET/POST /api/worlds/:id/characters` and `GET/PATCH/DELETE /api/characters/:id`, `GET /api/chats` (every chat of every world, most recently updated first), `GET/POST /api/worlds/:id/chats`, and `GET /api/chats/:id` (→ `{chat, world}`, plus `/messages`). No usable provider/model selection (no provider configured, or the requested or saved provider no longer exists) answers `400 {code:"no_provider", accepted:true, ...ids}` with the input saved and the draft marked failed; a provider without an API key is valid.

## Characters (M2 revision)

A character is always a world's own (`world_id` is required): `CHARACTER_PROFILE_FIELDS` in `shared/domain.ts` gives a required name and description plus lean authored fields, each optional and empty when unauthored; there is no attribute engine. Appearance, personality, and **intimacy** (sexual preferences and boundaries) are written as third-person fact. **Knowledge** (what they know that matters to the story, upbringing included), **memories** (events that matter to the story), and **inner thoughts** (what they want, fear, and keep to themselves) are written in first person, in the character's voice — that is how the narrator learns how they speak, so there is no separate speaking-style field. These fields are the authored baseline: play never writes to them. In the narrator prompt each character is one `<character name="Mira">` block holding an element per authored field — `<description>`, `<appearance>`, `<personality>`, `<intimacy>`, `<knows>`, `<remembers>`, `<thinks>`, then `<stats>` — with blank fields left out and `<`, `>`, `&` in authored text escaped so it cannot close the block. The **Knowledge boundaries** card tells the narrator that first-person text in a block is that character's own words, never its own or the player's, that characters speak and act only from what they know, remember, witnessed, or were told, that `<thinks>` stays unsaid unless the character chooses otherwise, and that the compendium is narrator background, not common knowledge.

Characters are listed and created under `GET/POST /api/worlds/:id/characters`; `GET/PATCH/DELETE /api/characters/:id` read, edit, and delete them (`DELETE` answers `{ok:true}`, `404` for unknown ids, and `409 {code:"conflict"}` while the character is the protagonist of any chat — discard those chats first). Deleting a character also deletes its relationships. Edits apply in place and live: the next reply of every chat sees them. A character cannot be created or listed outside a world (`/api/characters` itself answers `404`).

Each character may carry one picture. `PUT /api/characters/:id/avatar` takes the image's raw bytes (not multipart) with `content-type` `image/png`, `image/jpeg`, `image/webp`, or `image/gif`, capped at 2 MiB (`413` over); the magic bytes must match the declared type, and SVG or any other format is rejected (`415` unsupported type, `400` mismatch). Images are stored content-addressed — the lowercase hex sha256 of the bytes — in an `images` table, deduplicated by hash and immutable; `characters.avatar_id` points a character at one, and `DELETE /api/characters/:id/avatar` clears the pointer (the bytes stay). Every character response carries `avatar_id: string | null`, and `GET /api/images/:id` serves the stored bytes with the stored `content-type` plus `cache-control: public, max-age=31536000, immutable` (unknown ids: `404`). Like all mutations, avatar uploads require a trusted local Origin; `avatar_id` never enters narration prompts (images are display-only).

`POST /api/worlds/:id/characters` takes the profile fields plus the optional scene fields below; `PATCH /api/characters/:id` takes any profile field, the scene fields, `stats_enabled`, and a partial `stats` map (at least one field is required). A new character starts with `context_mode: "in_scene"`, `sticky: 4`, and stat tracking off.

**Chats choose the protagonist.** `POST /api/worlds/:id/chats {protagonist_id, opening?, title?}` (→ `201 {chat}`) requires `protagonist_id` to be a character of that world (anything else answers `404`); the title defaults to the first line of the opening, trimmed to 60 characters, else `New chat`. Every other character of the world is cast for that chat according to its context mode; the protagonist is always sent in full. `PATCH /api/chats/:id {title}` renames, and `DELETE /api/chats/:id` discards the chat (`409 {code:"busy"}` while a reply is pending). There is no per-world default protagonist: the new-chat form preselects the protagonist of the world's most recently updated chat.

**Cast context modes.** Each character carries `context_mode`, `summary` (one line, at most 200 characters, `""` by default), `aliases` (nicknames, same limits as entry keywords), and `sticky` (0–50, default 4), accepted by `POST` and `PATCH` above. `always` sends the full profile under the system prompt's `{{cast}}`, as before. `in_scene` — the default for new characters — sends only `- Name: summary (Protagonist → Name: status)` under `{{offstage}}`, the status taken from the chat's protagonist's relationship towards them when set, and sends the full profile only to replies whose recent messages mention their name or an alias, `[Name]` speaker tags included. `mentioned` sends nothing until they are mentioned. The chat's protagonist is always sent in full whatever its mode. The system prompt's `{{relationships}}` keeps only relationships between always-sent characters — the protagonist and `always` characters; any other relationship travels with the character it involves.

## World compendium (M2)

World entries — locations, lore, and opening-scene templates — persist in a `world_entries` table and are managed world-scoped under `GET/POST /api/worlds/:world_id/entries` and `PATCH/DELETE /api/worlds/:world_id/entries/:entry_id` (`200 {ok:true}` on delete). An entry id only ever resolves inside its own world's URL, so another world's entry is indistinguishable from a missing one (`404`).

Narration reads every non-scene entry of the world live — locations and lore, in creation order — so an edit or delete applies from the next reply. Scenes are opening templates only — selecting one copies its description into the new chat's editable opening in the UI and is never sent as grounding.

**Keyword entries (lorebook).** Entries accept optional `keywords` (up to 50 strings of 1–100 characters, trimmed and deduplicated ignoring case), `priority` (integer 0–1000, default 0), and `sticky` (integer 0–50, default 0). An entry without keywords is always in the system prompt's `{{compendium}}`. An entry with keywords is left out of it.

**Reply context.** For each reply, `server/lore.ts` scans the last 2 messages the model is sent (`LORE_SCAN_DEPTH`), or `2 + sticky` for a sticky character or entry; the latest input's direction counts, and before any history, the chat's opening is scanned instead. Matches are case-insensitive whole words or phrases. Triggered `in_scene` and `mentioned` cast members come first, in creation order, each with its relationships — except any naming a `mentioned` character not also triggered — then keyword entries whose name or a keyword matched, by descending priority, then creation order. They are appended to the latest player input for that one call as a `<reply_context>` block holding `<characters>`, `<relationships>`, and `<compendium>` (each left out when empty), before any `<ooc>` note, so the system prompt stays stable between turns and the context never enters later history; the **Reply context notes** card tells the narrator it is background, not player speech. Items go in while the note fits both `LORE_TOKEN_BUDGET` (10,000 tokens) and the room the narration budget leaves; the first item that does not fit is dropped along with every item after it. Each reply records `lore: {used, dropped}` (character and entry names; `null` when nothing was triggered), which Play shows as **Context: …** with any **Over budget: …**, and each swipe keeps its own.

Entry mutations, including deletion, require a trusted `Origin` header.

## Relationships, branches, and the narration budget (M3)

**Directional relationships** are world-owned. `GET /api/worlds/:id/relationships` returns `{relationships}`. A relationship runs between two characters of the world — `source_id` and `target_id` must identify characters of that world, else `400` — and a world holds at most 100 relationships. Create a directed pair with `POST /api/worlds/:id/relationships {source_id, target_id, how_met?, status?, known_facts?, stats?}`; reverse direction is a separate relationship, and duplicate ordered pairs are rejected. A relationship carries the fixed fields `how_met` and `status`, the `known_facts` list, and every relationship stat of the world — a new relationship starts with each stat at its default. `how_met` and `known_facts` are written in the source character's own words; `status` stays a short third-person label. The narrator gets each as a top-level `<relationship from="Mira" to="Oren">` block holding `<status>`, `<how_met>`, `<known_facts>` (one `- fact` per line), and `<stats>`, blank ones left out, and the **Knowledge boundaries** card tells it that first-person text there is the `from` character's. `PATCH /api/worlds/:id/relationships/:rid {how_met?, status?, known_facts?, stats?}` — last save wins, and `stats` merge into the existing values. `DELETE` removes that relationship. A relationship id resolves only inside its own world's URL.

**Grounding is per call and live.** Each narrator call is built from the world as it is at that moment — brief, non-scene entries, world stats, the chat's protagonist, the other characters by context mode, the world's relationships — plus **this chat's history only**. The system prompt depends only on the world and the prompt cards, never on the chat's progress. Every call's messages start with one opening message (`openingMessage` in `shared/narration.ts`): the chat's `opening` in an `<opening>` tag with a request to begin the story there, or a request for an opening that fits the world when there is none. A player turn sent before any narration joins that message, so the history always starts with a single user message that never changes for the chat. Nothing is dropped silently.

**Prompt caching.** Because the system prompt and the opening message stay the same from call to call and history only grows, every call begins with the previous call's request, which providers that cache the start of a prompt can reuse. Editing the world, a prompt card, or a message earlier in the transcript changes that prefix; the one-reply notes (reply context and OOC) are appended to the latest player message and never kept, so they only cost the message they were attached to. Each narration records `usage`: `estimate` (`system`, `history`, `context` — the system prompt, the history including the opening message, and the one-reply notes, counted with `shared/tokens.ts` when the call starts) and `provider` (`prompt_tokens`, `cached_tokens`, `completion_tokens` as reported on a normal finish, `null` when the provider reports none). The composer's token button shows the latest reply's split against the budget and the provider's cache rate.

**Context boundary.** One size budget covers every narrator call: `NARRATION_TOKEN_BUDGET` (40,000 tokens) in `shared/narration.ts` counts the narrator system prompt plus the chat's history (the opening message, selected player inputs, and completed narration), plus the request's direction note. Keyword lore is not counted against it: it only takes the room left over, and is dropped rather than refused. Tokens are counted with OpenAI's `o200k_base` encoding (`shared/tokens.ts`, via `gpt-tokenizer`) for every provider: exact for current OpenAI models, an approximation for others. It is checked per generation request — player turn, opening, and regenerate — and on message edits that grow a selected message; a request that would exceed it is refused with `413 {code:"context_limit", accepted:false}` and a message telling you to shorten the world's characters, entries or relationships, or start a new chat. No message is saved and nothing is ever truncated; the budget bounds the size of the model call, not the model's context window.

**Branches.** `POST /api/chats/:id/messages/:message_id/branch {title?}` (201 `{chat}`) starts a new chat from any message of the selected path: same world, protagonist, and opening, with the selected messages up to and including that message copied (content, speaker, direction, and lore; drafts and unselected swipes excluded, renumbered from 1, timestamps kept) and the title defaulting to `"<source title> (branch)"`. The branch is independent — the world is shared and read live like any chat's — and the source keeps playing unaffected. A message id from another chat answers `404`; a pending reply in the source answers `409 {code:"busy"}`.

## Stats (M5)

A **stat definition** is a reusable bounded meter: `applies_to` (`character` or `relationship`, immutable after creation), required `label`, `description`, `low_label`, and `high_label` text of at most 500 characters each, integer `min` < `max` and a `default_value` inside the range (magnitudes capped at 1000), and a `color` from the fixed palette `slate`, `red`, `orange`, `amber`, `green`, `teal`, `blue`, `violet`, `pink` (light and dark values live in `src/index.css` as `--stat-<token>`); labels are unique per kind within their scope (case-insensitive), and each scope holds at most 12 stats per kind. The **stat bank** is edited under **Settings → Stats** (`/settings/stats`) through `GET/POST /api/stats` and `PATCH/DELETE /api/stats/:id`; a fresh database seeds it with Health, Stamina, Stress, and Morale for characters and Trust, Affection, Respect, and Tension for relationships, all 0–10.

**World stats** are listed and created under `GET/POST /api/worlds/:id/stats` and share the `PATCH/DELETE /api/stats/:id` routes — one set of routes whose id resolves in the bank or any world. Bank stats are copied into a world when it is created (`POST /api/worlds {name, setting_brief, stat_ids?}`; unknown or non-bank ids answer `404`) or at any later time with `POST /api/worlds/:id/stats/import {stat_ids}` (→ `201 {stats}`), including after chats have messages. An added world stat gives its default to every opted-in character (character stats) or to every relationship (relationship stats) of that world, a changed `min`/`max` clamps existing values into the new range, and a deletion removes the value from every character and relationship of that world. Deleting a bank stat never touches worlds that already copied it.

**Stat tracking is per character and all-or-nothing**: a character either carries every character stat of its world or none (`stats_enabled` plus a `stats` map of stat id to integer). Characters start off. `PATCH /api/characters/:id` accepts `stats_enabled` and a partial `stats` map: turning tracking on fills every character stat with its default, turning it off clears the values, values may only be set while tracking is on (`400` otherwise), and unknown, non-integer, or out-of-range values answer `400`.

**Narration** renders the stats legend once — `Stats (scale and meaning):` followed by one line per stat with its kind, range, description, and both end labels — and adds values like `<stats>Health 7/10, Stress 2/10</stats>` to each opted-in character's block and `<stats>Trust 4/10</stats>` to each relationship block. `NarrationContext` carries `stats` (definitions with ids), the protagonist as `CharacterPrompt` (`id`, profile, `stats_enabled`, `stats`), the cast as `CastPrompt` (plus `context_mode` and `summary`), and relationships as `RelationshipPrompt` (`source_id`, `target_id`, `source_name`, `target_name`, `how_met`, `status`, `known_facts`, `stats`).

## Narrator prompt cards

The narrator system prompt is one global, ordered list of **prompt cards**, edited under **Settings → Prompt** (`/settings/prompt`) and applied live to every chat. A card has a `title`, a `body`, and an `enabled` switch; the prompt is the enabled bodies, top to bottom, separated by blank lines, each wrapped in a tag named after its title in snake case (`promptCardTag` in `shared/narration.ts`: accents dropped, every other run of non-alphanumerics an underscore, `_`-prefixed before a leading digit, `card` when nothing is left — **Narrator role** → `<narrator_role>`). Instruction cards refer to sections by those tags, so renaming a card renames its tag and may leave other cards pointing at the old one. Bodies may use the placeholders `{{world_name}}`, `{{world_brief}}`, `{{stats}}` (one `<stat>` element each), `{{protagonist_name}}`, `{{protagonist}}` (a `<character>` block), `{{cast}}` (`always` cast, `<character>` blocks), `{{offstage}}` (`in_scene` cast, one line each), `{{compendium}}` (one `<entry kind name>` element each), and `{{relationships}}` (`<relationship>` blocks); every value is escaped text or generated markup, so world text cannot close a card's tag. A card using any placeholder that is empty for the chat — no other characters, no stats — is left out, so its section never introduces nothing. Any other `{{…}}` is refused on save. The chat's opening is not a placeholder: it is the first message of the history (see **Grounding**). A fresh workspace starts with `DEFAULT_PROMPT_CARDS` (`shared/narration.ts`), which include the **Elsewhere** card, which tells the narrator not to bring offstage characters in unprompted, the **Knowledge boundaries** card, which keeps characters to what they know, and the **Reply context notes** card; the `[Name]` speaker-tag and OOC cards are editable too, so disabling them stops speaker attribution and directions from working.

Cards are served by `GET /api/prompt-cards` (`{cards}` in order), created with `POST {title, body?, enabled?}` (appended last; `201 {card}`), edited with `PATCH /api/prompt-cards/:id {title?, body?, enabled?}`, and deleted with `DELETE`. `PUT /api/prompt-cards/order {ids}` sets the order and must name every card exactly once; `POST /api/prompt-cards/reset` replaces every card with the defaults. Both answer `{cards}`. Edits apply from the next narrator call, and the narration budget counts the rendered prompt.

## Development workspace

The schema carries a version (`PRAGMA user_version`, currently 8). There are no migrations or compatibility layer: a workspace database created by an older schema is refused at startup with an error naming the file and telling you to delete it, and the Vite proxy answers every `/api` request with 500 meanwhile. Point `STORYFOLD_DATA_DIR` at a fresh directory to use the current schema; this does not delete, reset, or overwrite the existing database, which remains untouched:

```sh
STORYFOLD_DATA_DIR=$HOME/.local/share/storyfold-m5 bun run dev --host
```

`bun run dev` starts the full stack (API and Vite) against that data directory. Backend tests always run against isolated temporary databases.

## UI components

The composer, transcript scroller, tooltips, and theme indicator are adapted from [beUI](https://beui.dev) registry sources (installed by copying and trimming the component code, not via the shadcn CLI):

- [Prompt Input](https://beui.dev/components/agents/prompt-input) — composer form, keyboard submission with IME safety, send-button motion, and a Stop control during generation. The model picker is a Radix Dropdown Menu with one submenu of models per provider; attachment UI is omitted. Auto-grow uses the repo's `field-sizing` CSS instead of the registry's measurement mirror, so browsers without `field-sizing` show a fixed-height scrolling composer. Focus uses the existing rounded composer border; forced-colors mode retains a visible textarea outline.
- [Message Scroller](https://beui.dev/components/agents/message-scroller) — reader-aware transcript viewport. Deviations: viewport resizes (composer growth, mobile drawer) re-align the live edge instantly while you are following, wheel, touch, and upward keyboard scrolling interrupt an in-flight follow, and the optional message navigation rail is omitted.
- [Tooltip](https://beui.dev/components/motion/tooltip) — hover/focus tooltips on the sidebar rail.
- [Tabs](https://beui.dev/components/motion/tabs) — shared-layout spring indicator adapted to the settings theme radios, without tab panels or overflow controls. The pill slides between choices; reduced-motion users get an instant selection change.
- [Collapsible](https://beui.dev/components/motion/collapsible) — prompt card expand/collapse on **Settings → Prompt**. Controlled only, with the repo's button styling on the trigger; the `render` slot is omitted. The cards' reorder list shares its layout spring, so expanding a card moves its neighbours without stretching their text.

Dependencies added for these components: `motion` (reduced-motion-aware animation), `@floating-ui/dom` (tooltip positioning), `lucide-react` (send icon), and `clsx` + `tailwind-merge` (the `cn` class helper).

The User menu uses Radix Dropdown Menu; page navigation uses React Router. Settings theme choices use native radios for keyboard navigation and accessible selection.
